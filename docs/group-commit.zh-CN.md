# 合并提交的规则

[English](group-commit.md) · 简体中文

很多 goroutine 各自用自动提交写一行时，每一行都要付一次提交的代价，SQLite 同一时刻又只有一个写入者，大家只能排队。驱动把这些写入放进同一个事务，只提交一次。

这是驱动替调用方做的决定，调用方并不知道自己被合并了。下面的规则守住两件事：一条语句执行过就不再执行第二次，被合并的语句除了第五节列出的不同，结果和它单独执行时一样。改这部分代码之前，先把这份文档读完。

## 一、哪些语句能合并

1. **只合并自动提交的 INSERT、UPDATE、DELETE（含 REPLACE、UPSERT、以 WITH 开头的写语句），而且只写 main 库。** 只有 `Exec` 会合并，`Query` 不会。`EXPLAIN` 不合并，它不写任何东西。原因：别的语句（DDL、PRAGMA、ATTACH）会改连接或 schema，换个连接执行结果就不一样。
2. **用户事务里的语句永远不合并。** `stmt.go` 的 `exec` 里，连接不在事务中、没持有写锁、没改过自己、语句可以合并，几个条件都满足才进队列。原因：用户事务的边界是调用方定的，驱动不能把别人的语句塞进去，也不能把它的语句拿出来。
3. **语句不能碰只属于自己连接的东西**，在准备语句时由 `engine/os.c` 的授权回调 `goClassify` 判断：
   - 不碰 temp 库和 ATTACH 进来的库
   - 不经触发器写表（触发器可能是临时的）。只在触发器里读或调用函数的，不受这条限制
   - 不写也不读 Go 虚表（Go 代码的状态 SQLite 撤不回来，每个连接的表实例也可能不同）
   - 不调用 `last_insert_rowid()`、`changes()`、`total_changes()`（它们读的是连接自己的计数）
   
   SQLite 在准备期间嵌套准备的语句（比如 R*Tree 第一次被连接用到时准备的影子表语句）也会经过这个回调。它们可以让外层语句不能合并，但永远不会让外层语句变成「写 main 库」。
4. **schema 变了，语句可能变得不能合并。** SQLite 会在 `sqlite3_step` 开头重新编译它，这时它还什么都没做。如果这发生在替别人跑批的连接上，而语句已经不能合并，`goClassify` 让这次准备失败，语句退回调用方自己的连接执行，之后再重新分类。拒绝如果落在编译期间嵌套准备的语句上（比如虚表连接时准备的语句），也记在外层语句的 Parse 上，让外层的准备失败。原因：虚表可能吞掉嵌套语句的错误继续执行（带辅助列的 R*Tree 就会），那样被拒的语句就真的执行了。

## 二、哪些连接能互相代跑

5. **只在同一个文件、同一个合并 key 的连接之间代跑。** key 由规范化后的文件名和 URI 参数、按顺序的 `_pragma` 设置、Go 函数和虚表模块的那一组构成（`sqlite.go` 的 `NewConnector`）。DSN 相同、用同一批 `Register` 建的两个连接器共用一个 key。用 `NewConnector(dsn, opts...)` 自带选项的连接器有自己的 key，不和别人共用。注册是建连接器那一刻的快照，之后再 `Register` 不改变已有的连接器。原因：代跑的连接必须有调用方连接的一切，语句才能得到同样的结果。
6. **永久退出合并的连接**（不交出语句，也不替别人跑）：
   - 准备过会改连接的语句：设值的 PRAGMA、ATTACH、DETACH、建或删临时对象。从准备那一刻算，不管它有没有执行、准备有没有成功
   - 以只读方式打开
   - DSN 里打开了 `defer_foreign_keys`（SQLite 每个事务结束会关掉它，同一 DSN 的连接因此不一样）
7. **暂时不能合并的连接**，状态结束后恢复：在事务中（包括只读事务、还没读完的查询持有的读快照）。已关闭、已出错、已失效的连接不替别人跑。

## 三、一批怎么跑

8. **一个文件在本进程里只有一把写锁**（按文件本身找，不按路径名）。内存数据库没有这把锁，也不合并。别的进程只经过 SQLite 自己的文件锁。
9. **调度**：
   - 锁空闲时，语句拿锁直接执行，不等着凑批。只有一个写入者时没有额外开销。
   - 锁被占着时，语句进队列，记下它的序号。
   - 持锁的连接还锁之前，从队列里取出和自己同一 key 的语句（一批最多 256 条），在自己身上跑：`BEGIN IMMEDIATE`，每条语句各套一个 `SAVEPOINT` 和 `RELEASE`，最后 `COMMIT`。
   - 然后调用复制的 committed 回调（不管这一批成没成功，持锁者自己之前提交的事务可能还没通知），再把锁交给等锁的写者和队首语句里序号最小的那个。
   - 锁交给一条排队的语句时，它在自己的连接上领一批：自己排第一，再捎上同一 key 的语句。它还锁时还可能再取一批，然后才交出去。
   
   序号保证的是排队位置和交锁时的先后，不保证所有 SQL 按全局到达顺序执行：取批时会捎上同一 key 里比某个等锁写者晚到的语句。原因：只按 key 取批是合并能快的前提，按序号交锁是为了没有谁会一直轮不到。
10. **调用了没标 `Innocuous` 的 Go 函数，这一批就到这条为止。** 标量函数被调用时、聚合或窗口函数每组建状态时，在连接上做标记（`markEffects`）。这条语句跑完（成功或单条失败）就提交，后面还没执行的语句放回队列，保留原来的序号。触发器、CHECK、生成列、DEFAULT 里间接的调用也算，没真正调用就不算。原因：这种函数可能有副作用，批越小，失败时被连累的语句越少。代价：调用这种函数的写入基本得不到合并的好处。排序规则没有这个标记，它必须本来就没有副作用。
11. **有虚表参与事务时（比如 FTS5），每条语句后面在它自己的 `SAVEPOINT` 里再跑一对 `SAVEPOINT` 和 `RELEASE`。** 原因：FTS5 要到下一个 `SAVEPOINT` 或 `COMMIT` 才写索引，不这样做，写索引的失败会落到下一条语句或整批头上。

## 四、每个阶段失败时谁拿到什么

**一律不重跑。** 驱动不知道一条语句除了改数据库还做了什么（Go 函数的副作用、虚表的外部状态），重跑可能让这些事发生两次。整批失败是合并提交的代价。

每个取进批的请求，最后只会有一种结局：拿到结果，或者放回队列，二者只发生一次。下面「执行过」指它的 `sqlite3_step` 被调用过。

| 阶段 | 结果 |
| --- | --- |
| 还在队列里，context 结束或等锁超时 | 从队列里拿掉，拿到 context 的错误或 `SQLITE_BUSY`。没执行，不影响别人。调用方已经不在队列里等、转去等结果之后才放回队列的请求，不会再被拿掉：它等下一批或拿到锁时给它的结果 |
| 已取进批，轮到它时 context 已经结束 | 不执行，单独拿到 context 的错误，不算进这一批 |
| 已取进批，准备或绑定参数失败 | 没执行，单独拿到自己的错误，不算进这一批 |
| 重新编译时被拒（第 4 条） | 撤销它的 `SAVEPOINT` 成功后放回队列，轮到它时在调用方自己的连接上执行。它什么都没做过，这不算重跑。撤销失败按「事务被结束」处理 |
| `BEGIN IMMEDIATE` 失败 | 没有语句执行过。这一批全部拿到 BEGIN 的错误 |
| 语句失败，事务还在（比如违反约束） | 先记下它自己的错误和 SQLite 替它留下的行（`OR FAIL` 会留下失败之前的行）。最终结果看这一批的结局 |
| 语句留下没解决的延迟外键 | 用 `ROLLBACK TO` 撤销它，记下单独提交时会拿到的外键错误。最终结果看这一批的结局 |
| 虚表写索引失败，事务还在 | 撤销这条语句，记下它的错误。最终结果看这一批的结局 |
| 一条语句或驱动自己的 `SAVEPOINT`、`ROLLBACK TO`、`RELEASE`、写索引让整个事务结束了（被中断、IO 错误、磁盘满、内存不够、`OR ROLLBACK`、`RAISE(ROLLBACK)`、排序规则 panic 等） | 当时在执行的请求拿到结束事务的那个错误。它之前执行过的请求，不管当时成功还是单条失败，全部改拿 `SQLITE_ABORT_ROLLBACK`（516），`Unwrap()` 指向结束事务的那个错误。它之后还没执行的请求放回队列，保留原来的序号 |
| 驱动的 `ROLLBACK` 也失败，事务还在 | 按上一行给结果。这个连接标为作废，事务还开着，它就一直拿着写锁。`database/sql` 丢弃它时关闭它，关闭会回滚事务并交还写锁。领这一批、自己没执行的那个拿到锁的请求得到 `driver.ErrBadConn`，由 `database/sql` 换个连接执行 |
| 第 10 条切批 | 已执行的部分照常提交，没执行的放回队列 |
| `COMMIT` 成功 | 每个执行过的请求拿到它自己记下的结果：成功的拿到 `RowsAffected` 和 `LastInsertId`，单条失败的拿到自己的错误 |
| `COMMIT` 失败 | 这一批执行过的请求全部拿到 COMMIT 的错误，包括之前单条失败的。不重跑 |

补充说明：

- **判断事务有没有结束，看连接实际的状态（`AutoCommit()`），不看错误码。** 同一个错误码有时只回滚单条语句，有时回滚整个事务，由 SQLite 当时的状态决定。
- **「还没执行」是精确的。** 失败那条之后的请求，在这一批里只是从队列挪进了一个 Go 切片，没有在代跑的连接上准备、没有 `SAVEPOINT`、没有绑定参数、没有 `sqlite3_step`，Go 函数一次都没被调用。重新编译被拒而退回的请求不一样：它准备过、step 过，只是 step 在执行任何东西之前就失败了。
- **执行中 context 结束，驱动会尝试中断。** SQLite 返回中断错误并结束了事务，就按「整个事务结束」处理。语句已经执行完、来不及中断的，就当它正常执行过。context 不管 `BEGIN`、`SAVEPOINT`、`COMMIT`，也不能撤销已经提交的写入。
- **领头的请求也不重跑。** 拿到锁的请求自己领批时，只要它执行过，结果就按上表给，不能再退回自己的连接执行。只有重新编译被拒时才退回。
- **一旦被取进批，调用就要等这一批的结局。** 这时 `busy_timeout` 和 context 都不再限制调用的总时长。
- **last_insert_rowid**：每个请求单独记下自己执行后的值，最后写回调用方的连接。没执行、放回队列、被拒退回的请求保持调用方原来的值。拿到错误的请求，调用方连接上的值和单独执行时一样，按 SQLite 已经做过的操作算（SQLite 回滚时不恢复这个值）。

## 五、和单独执行的区别

12. **一条本来会成功的语句，可能因为同批别人的失败拿到 `SQLITE_ABORT_ROLLBACK`。** SQLite 定义这个码是「语句所在的事务被回滚了」，驱动在合并失败时给被连累的请求合成它。自动提交的语句单独执行时不会拿到这个码，看到它就知道是被同批连累的。
    - 它表示这次数据库写入被回滚了，不表示外部副作用没发生（这一批里的 Go 函数可能已经被调用过），也不保证这条语句重试就一定成功。要不要重试，调用方自己判断。
    - `Unwrap()` 指向 SQLite 报出的原因。别人的 context 结束、中断了这一批时，原因是 `SQLITE_INTERRUPT`，不是 `context.Canceled`：`errors.Is(err, context.Canceled)` 只在你自己的 context 结束时为真。
13. **单条失败的语句，最终也可能拿到 516 或 COMMIT 的错误**，而不是它自己的错误，因为它留下的东西也随这一批回滚了。结束事务的那条语句，也可能是因为同批前面一条后来被回滚的写入才失败的：报 UNIQUE 冲突，冲突的那行最终却不在库里。
14. **`changes()` 和 `total_changes()` 属于实际执行语句的连接。** 被别的连接代跑时，调用方连接上的这两个计数不算它，代跑的连接却算上了别人的语句。`RowsAffected()`、`LastInsertId()` 和调用方连接上的 `last_insert_rowid()` 都按请求单独记，是对的。
15. **一批的写入在 `COMMIT` 时一起可见。** 一批里靠前的语句，要等整批提交后才被提交之后开始的读看到。已经打开的读事务仍然看旧的快照，和单独执行一样。
16. **复制不提供批内单条语句的恢复点。** 一批是一个 SQLite 事务。复制的一个 TXID 是一次暂存，可能包含好几批或别的事务（见 [replication.zh-CN.md](replication.zh-CN.md)）。

## 六、错误怎么判断

驱动导出错误类型 `sqlite.Error`：`Code()` 是主错误码，`ExtendedCode()` 是扩展码，`Unwrap()` 是原因。错误码有同名常数（`sqlite.BUSY`、`sqlite.CONSTRAINT`、`sqlite.ABORT_ROLLBACK` 等）。

```go
var e *sqlite.Error
if errors.As(err, &e) && e.ExtendedCode() == sqlite.ABORT_ROLLBACK {
	// 被同批别的语句连累，这次写入已回滚
}
```

驱动不把这类错误包成 `driver.ErrBadConn`，否则 `database/sql` 会自动重试，又成了重跑。唯一给 `driver.ErrBadConn` 的，是连接作废、自己又没执行过的请求（见第四节）。

## 七、改这部分代码时必须守住的

- **不重跑执行过的语句。** 这条同时约束 `runBatch`、`lead` 和它失败后退回自己连接的分支、连接作废的路径。任何新的失败路径，都要说清楚执行过的请求拿到什么。
- **放回队列只有这几种**：失败点或切批点之后、在这一批里没碰过的请求，重新编译被拒并撤销成功的请求，以及代跑的连接已经知道不能合并的语句（没有 `SAVEPOINT`，没有 step）。都保留原来的序号、context、参数和原来的 last_insert_rowid，不关闭 `done`。
- **每个请求只结束一次**，`done` 只关闭一次。领头请求的路径和放回队列的路径都要保证锁最终交出去，复制的 committed 回调在交锁之前调用。
- **新加一种语句能合并之前**，先在 `goClassify` 里证明它不碰连接自己的东西，再加测试。拿不准就不合并，只会慢，不会错。
- **新加一种 Go 回调**（函数、虚表方法等），要说清楚它在批里出错、有副作用、被调用多次时会发生什么，以及它算不算第 10 条的标记。
- **每条规则都要有测试守着。** 相关测试在 `merge_test.go`、`fault_test.go`、`functions_test.go`、`builtin_test.go`、`vtab_test.go`、`group_test.go`、`replhook_test.go`、`readtx_test.go` 和 `internal/csqlite` 里。测试要按错误类型断言每个请求的结局和最终的行，不能只数成功的行。
- **改规则时同步改**：这份文档的中英两版、[AGENTS.md](../AGENTS.md) 的硬约束、[architecture.zh-CN.md](architecture.zh-CN.md) 的摘要、`functions.go` 等公开文档，以及受影响的测试。
